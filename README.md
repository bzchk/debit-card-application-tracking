# Учёт заявок на дебетовую карту

Демонстрационный проект ИТ-аналитика. Он показывает, как связать события оформления карты, посчитать заявки без повторов и найти ошибки в журнале. Все данные синтетические.

## Запуск веб-стенда

Нужен Python 3.10 или новее. Из корня репозитория запустите:

```sh
python app.py
```

Откройте `http://127.0.0.1:8000`. Для другого порта используйте `python app.py --port 8080`.

Попробуйте открыть форму для `A107`, отправить заявку и активировать карту. Затем отправьте заявку повторно и проверьте список ошибок. Кнопка «Повторить» в журнале имитирует повторную доставку того же события: счётчики и журнал сохраняют прежнее состояние.

Веб-стенд запускает запросы из папки `sql` в SQLite, которая входит в стандартную библиотеку Python. Данные живут в памяти до остановки приложения. Кнопка «Сбросить пример» загружает исходный набор.

## Сценарий

При открытии формы приложение создаёт черновик с идентификатором заявки. Отправка формы и активация карты записываются с тем же идентификатором. Если связь пропала после отправки, приложение может повторить запрос с тем же идентификатором. В отчёте такая попытка считается частью существующей заявки.

| Событие | Что означает |
| --- | --- |
| `form_opened` | Клиент открыл форму, система создала черновик |
| `application_submitted` | Система приняла заявку |
| `card_activated` | Клиент активировал карту, выданную по заявке |

У каждого события есть собственный `event_id`. Повторная доставка одного события сохраняет этот идентификатор. Две отдельные попытки отправки могут иметь разные идентификаторы событий, но относятся к одному `application_id`.

## Запуск SQL в PostgreSQL

Нужны PostgreSQL и клиент `psql`. Из корня проекта запустите все файлы в одном сеансе. Временные объекты удалятся при его завершении.

```sh
psql -X -v ON_ERROR_STOP=1 -d postgres -f sql/01_schema.sql -f sql/02_sample_data.sql -f sql/03_report.sql
```

Если сервер требует параметры подключения, укажите хост и пользователя через `-h` и `-U`.

## Что проверяет пример

В тестовом журнале шесть заявок. Для итогового статуса используется первое событие каждого типа. В отчёт попадают только заявки, открытие формы которых зафиксировано. Некорректная активация не повышает статус заявки.

| Статус | Количество |
| --- | ---: |
| Форма открыта | 1 |
| Заявка отправлена | 3 |
| Карта активирована | 1 |

Отдельная выборка показывает повторную отправку заявки `A101`, активацию без отправки у `A103`, активацию раньше отправки у `A104` и отсутствие открытия формы у `A105`. Повторная доставка события с тем же `event_id` в журнале не размножается.

Проект демонстрирует анализ журнала и правила отчётности. За защиту от повторного создания заявки при сетевом сбое отвечает сервис оформления.
